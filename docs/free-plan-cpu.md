# Workers Free CPU 한도(요청당 10ms) 대응 — 설계

상태: 설계 확인 대기 · 작성 2026-11-25

## 배경

Cloudflare 계정이 Workers Free 요금제다. Free는 요청 1건(정기 실행 포함)당 CPU 10ms가 한도다.
`account-bot-production`은 중앙값부터 이 한도를 넘는다. 아직 한도 초과로 끊긴 요청은 없다.

## 현재 측정 (운영, 2026-11-18~24, Actions `metrics`)

- 전체: 요청 37건 모두 success, `exceededResources` 0건. CPU P50 18.5ms, P75 27.1ms, P99·최대 64.8ms. 외부 호출 합계 103건.
- 정기 실행(매일 08:00 KST 1건): 40.3 / 64.8 / 54.6 / 44.9 / 50.4ms. 외부 호출 1~18건.
- 텔레그램 명령(11/21 집중 사용): 15분 구간별 P50 9.1~18.5ms, 최대 15.3~50.1ms.
- 요청이 드물어서 대부분 새 인스턴스의 첫 요청이다.

## 명령별 측정 (로컬 Node, 계획 85개·이력 약 260개 합성 자료, DB 시간 제외)

절대값은 운영(workerd)과 다르다. 순위와 원인 파악용이다.

| 경로 | 첫 실행 | 반복 실행 |
|---|---|---|
| 일간보 작성 | 18.1ms | — |
| `/weekly` | 19.8ms | 2.7ms |
| 주간보 작성(정기) | 15.7ms | — |
| `/추천` | 10.6ms | 2.8ms |
| `/모으기` | 7.5ms | 2.7ms |
| `/모으기시점` | 3.3ms | 1.2ms |
| `/모으기이력` | 1.7ms | 0.5ms |
| `/모으기설정` | 1.5ms | 0.7ms |
| `/help` | 0.1ms | 0.0ms |

확인된 원인:

1. **`Intl.DateTimeFormat` 첫 생성.** 로컬 6.4ms(같은 계정 PORTFLOW의 운영 측정은 약 21ms). 요청마다 최대 4곳에서 만든다: 설정 검증(`operating-worker.mjs:26`), 정기 실행 시각 계산(`boundary.mjs:47`, `operating-worker.mjs:102`), 보고서 기준 시각(`assets-report.mjs:34`). CPU 프로파일에서 단일 함수로는 `localTime`이 가장 컸다(약 8ms).
2. **첫 실행 비용.** 반복 실행은 3ms 이하인데 첫 실행은 7~20ms다. 보고서 작성 코드(계획 60~85개 × 문자열·Decimal 처리)를 처음 실행하는 비용이다. 운영 요청은 대부분 첫 실행이다.
3. **정기 실행의 추가 작업.** 보고서 작성에 더해 발송 뒤 시장 신호 갱신(외부 응답 JSON 파싱, 하루 17건 안팎)을 같은 실행에서 한다.

## 목표

- 운영에서 모든 요청의 CPU 최대값 10ms 미만, `exceededResources` 0건.
- 기능과 응답 내용은 그대로 둔다. 계산 결과가 달라지면 안 된다.
- 10ms 안으로 못 줄이는 경로가 남으면 숨기지 않고 대안과 함께 보고한다.

## 제약

- 주문·계좌 연동 추가 없음. 비밀값·개인 자료를 저장소·로그에 넣지 않는다.
- 유료 서비스 없음. R2는 쓰지 않는다. D1·Cron은 Free 허용 범위다(하루 요청 37건/주, 외부 호출 요청당 최대 20건 < 50건).
- DB schema·idempotency·`UNKNOWN` 전송 규칙을 바꾸지 않는다.
- 다른 프로젝트의 Worker·DB는 건드리지 않는다.
- 운영 배포는 단계마다 승인을 받는다.

## 단계와 완료 기준

각 단계는 배포 뒤 실제 사용(명령 몇 개 + 다음 정기 실행)을 거쳐 `metrics`로 측정하고 보고한다.

1. **시간대 계산을 산술로 교체**
   - `Asia/Seoul`(UTC+9, 서머타임 없음)은 `Intl` 없이 계산한다. 다른 시간대 설정은 기존 `Intl` 경로를 그대로 쓴다.
   - 완료 기준: 기존 테스트 전부 통과(보고서 문구·정기 실행 시각 동일). 새 테스트로 산술 결과가 `Intl` 결과와 같은지 여러 시각(자정 경계, 연말, 윤년)에서 확인. 운영 측정에서 명령·정기 실행 CPU가 내려간 수치를 보고.
2. **요청당 고정 비용 줄이기**
   - 1단계 뒤 측정으로 남은 큰 항목을 다시 찾아서 줄인다. 후보: 같은 요청에서 계획 목록을 여러 번 읽고 변환하는 중복, 응답과 무관한 준비 작업.
   - 완료 기준: 테스트 전부 통과, 응답 내용 동일. 운영 측정에서 가벼운 명령(`/모으기설정`, `/모으기이력`, `/help`)의 최대값 10ms 미만.
3. **정기 실행 분리** (1·2단계 측정을 보고 필요할 때만, 설계 재확인)
   - 안 A: 발송과 신호 갱신을 다른 Cron 실행으로 나눈다. 가장 단순하다.
   - 안 B: 보고서 작성을 GitHub Actions로 옮기고(D1 REST API로 같은 DB 사용) Worker는 저장된 보고서를 발송만 한다. 텔레그램 토큰은 Worker에만 둔다. Actions 예약이 늦을 수 있어 지연 대비가 필요하다.
   - 완료 기준: 정기 실행 CPU 최대값 10ms 미만, 일간보·주간보가 제시간에 한 번만 도착.
4. **무거운 명령** (`/weekly`, `/추천`, `/모으기`; 1~3단계 뒤에도 넘으면)
   - 측정 결과와 함께 대안을 보고한다: 미리 계산해 저장 / 응답 축소 / 현 상태 유지(초과 허용) / Paid($5/월).
5. **문서화**: 단계별 측정값·결정·남은 이슈를 이 문서에 기록.

## 되돌리기

- 각 단계는 Worker 코드만 바꾼다. 문제가 생기면 Actions `rollback`으로 직전 버전에 돌아간다.
- 3단계 안 B를 택하면 그때 별도 되돌리기 절차를 설계에 적는다.
