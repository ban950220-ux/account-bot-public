# 무거운 응답 미리 계산 (Free CPU 대응 안 A) — 설계

상태: 설계 확인 대기 · 작성 2026-11-27 · 상위 문서 `docs/free-plan-cpu.md`

## 배경

- 무료 요금제의 CPU 한도는 요청 1건당 10ms다. 넘으면 요금은 없지만 요청이 끊길 수 있다.
- 운영 측정값

| 요청 | CPU |
|---|---|
| 일간보 | 32ms |
| `/모으기` | 40ms |
| `/policy` | 12ms |
| `/help` | 9ms |

- 정밀 측정(`docs/free-plan-cpu.md` 2단계-가)
  - 무거운 응답은 계획 86개분의 계산과 첫 실행 비용이 겹친다. 부분 수정만으로는 10ms 미만이 어렵다.
  - `localeCompare` 첫 호출 하나가 5~9ms다.

## 목표

- 무거운 응답은 GitHub Actions에서 미리 계산해 D1에 저장한다. Actions에는 CPU 한도가 없다.
- Worker는 저장된 결과를 읽어 보내기만 한다.
- 대상
  - 명령: `/모으기`, `/weekly`, `/추천`
  - 정기 보고서: 일간보, 주간보
  - 정기 실행의 신호 갱신(5년 주간 차트 해석)도 Actions로 옮긴다.
- 응답 내용은 지금 직접 계산한 결과와 글자 하나까지 같아야 한다. 차이는 첫 줄의 기준 시각 표시뿐이다.
- 운영에서 저장 결과를 쓴 요청의 CPU가 10ms 미만이어야 한다.

## 사용자 결정 (2026-11-27)

- 미리 계산은 1시간마다 한다. 답장에 기준 시각을 표시한다.
- 계획을 바꾸면 자동으로 다시 계산한다. Worker가 Actions 실행을 요청한다.
- 미리 만든 결과가 없거나 쓸 수 없으면 지금처럼 Worker가 직접 계산한다.

## 구조

```
GitHub Actions (매시간 + 계획 변경 시 요청)
  └─ precompute: D1 REST API로 읽기 → 기존 gateway·보고서 코드로 계산 → cloud_precomputed에 저장
Cloudflare Worker
  └─ 명령·정기 실행: 입력 지문 확인 → 맞으면 저장 결과 발송 / 아니면 기존 직접 계산
```

### 새 테이블 `cloud_precomputed` (추가형 migration)

| 열 | 내용 |
|---|---|
| `kind` | `recurring` / `weekly_cmd` / `recommend` / `daily_report` / `weekly_report` (기본 키) |
| `period_key` | 보고서는 `daily:20261128`처럼 대상 날짜를 넣는다. 명령은 빈 값 |
| `input_fingerprint` | 계산에 쓴 입력의 지문 |
| `computed_at` | 계산 시각(UTC) |
| `body` | 완성된 답장 문구 |

- 같은 `kind`는 덮어쓴다. 이력은 남기지 않는다(파생 자료라서).
- 기존 테이블, revision, fence 규칙은 바꾸지 않는다.

### 입력 지문

응답이 기대는 저장 자료가 바뀌었는지 Worker가 싸게 확인하는 값이다. SQL 1회로 아래 항목의 최신 행 번호와 행 수를 읽어 합친다.

- 계획 revision
- 보관·복원 이벤트
- 목표·정책 revision
- thesis revision
- 수동 입력(메리츠) revision
- cutover 상태

시세와 신호는 지문에 넣지 않는다. 대신 계산 시각으로 신선도를 본다.

### Worker가 저장 결과를 쓰는 조건

다음을 모두 만족하면 저장 결과를 쓴다. 하나라도 어긋나면 기존 방식으로 직접 계산한다.

1. 행이 있다.
2. `input_fingerprint`가 지금 지문과 같다(계산 뒤 계획 변경 없음).
3. 계산된 지 2시간 이내다. 매시간 실행에 GitHub 예약 지연(5~30분)을 더한 값이다.
4. 보고서는 `period_key`가 오늘 보고서와 같다.

답장 첫 줄에는 `🕘 기준 HH:MM KST`를 붙인다. 직접 계산한 답장에는 붙이지 않는다.

### Actions `precompute` workflow (새 파일)

- 실행 시점
  - 매시간 예약
  - 평일 07:10 KST 예약(일간보용)
  - 수동 실행
  - Worker의 요청(`workflow_dispatch` API)
- 동시 실행은 하나로 묶는다(`concurrency`). 요청이 몰려도 마지막 계산만 남는다.
- D1 접근은 기존 `production` Environment의 Cloudflare 토큰을 쓴다(D1 권한 있음).
- 공개 저장소라 실행 로그가 공개된다. 로그에는 종류별 성공/실패, 글자 수, 소요 시간만 출력한다. 응답 문구, 종목, 금액은 출력하지 않는다.
- D1 REST 어댑터
  - Worker의 D1과 같은 `prepare/bind/first/all/run/batch` 모양으로 만든다.
  - 쓰기는 `cloud_precomputed`와 시세·신호 캐시(`cloud_market_cache`)만 허용한다. 다른 쓰기는 예외로 막는다. 계획이나 발송 상태를 Actions가 바꿀 수 없게 하기 위해서다.
- 계산은 기존 코드를 그대로 쓴다. 답장 문구 생성 부분을 함수로 분리하고, Worker와 Actions가 같은 함수를 부른다.

### 계획 변경 시 재계산 요청

- Worker가 계획을 바꾸는 명령이 성공하면 GitHub API에 이 workflow 실행을 요청한다.
  - 대상 명령: `/모으기설정`·`추가`·`변경`·`삭제`·`복원`, `/모으기시점` 반영, `/목표` 저장, `/추천적용`, thesis 저장
- 필요한 것: 사용자가 GitHub fine-grained token을 만든다.
  - 저장소: `account-bot-public` 하나
  - 권한: Actions 읽기·쓰기만
  - 이 토큰을 Worker secret `GITHUB_DISPATCH_TOKEN`에 넣는다. 넣는 방법은 단계 4에서 안내한다.
- 요청이 실패해도 명령 결과에는 영향이 없다. 다음 매시간 계산에서 따라잡는다.
- 요청은 외부 호출 1건이다. CPU 비용은 작다.

### 일간보·주간보

- Actions가 07:10 KST와 매시간 실행 때 오늘 보고서를 미리 만든다.
- 08:00 정기 실행은 위 조건에 맞으면 저장 문구를 기존 outbox(발송 대기열)에 넣는다. 아니면 기존 방식으로 직접 계산한다.
- 기간 선점(claim), outbox, 한 번만 발송 규칙은 그대로다. 바뀌는 것은 문구를 어디서 가져오느냐뿐이다.
- 발송 뒤의 신호 갱신은 Worker에서 빼고 Actions 매시간 실행에서 한다.

## 범위 밖

- `/추천적용`: 적용 시점에 다시 검증해야 하므로 Worker가 계속 직접 계산한다(현재 무거움). 이후 별도 검토한다.
- 가벼운 명령(`/help` 9ms)의 고정 비용: 단계 1에서 `localeCompare`만 먼저 처리한다. 나머지는 측정 뒤에 정한다.
- `/assets`, `/rebalance`, `/분석`, `/종목` 등: 측정상 한도 근처라 이번에는 제외한다. 운영 측정에서 넘으면 같은 방식으로 추가한다.

## 제약

- 주문·계좌 연동 추가 없음
- 텔레그램 토큰은 Worker에만 둔다. Actions는 텔레그램에 보내지 않는다.
- 비밀값과 개인 자료는 저장소와 로그에 넣지 않는다.
- 기존 DB schema, idempotency, `UNKNOWN` 전송 규칙은 바꾸지 않는다. 새 테이블은 추가형 migration으로만 만든다.
- 운영 배포와 migration은 단계마다 승인을 받는다.
- 유료 서비스는 쓰지 않는다.
  - 공개 저장소 Actions는 무료다.
  - D1 읽기량은 시간당 수천 행 수준으로 Free 한도(하루 500만 행)보다 훨씬 작다.

## 단계와 완료 기준

1. **`localeCompare` 제거**
   - 정렬 순서가 같은 자체 비교 함수로 바꾼다. 직접 계산 경로에도 이득이다.
   - 완료 기준
     - 실제 쓰는 문자 범위(영문 대소문자, 숫자, `.` `-` `:` `_` 공백, 한글)의 무작위 문자열 수만 개에서 기존 `localeCompare`와 결과가 같다.
     - 전체 테스트 통과
     - 운영 측정에서 `/모으기` CPU가 내려간 수치를 보고한다.
2. **답장 생성 분리와 D1 REST 어댑터** (운영 영향 없음)
   - 완료 기준
     - 같은 자료와 시각에서 Actions 경로로 만든 문구가 Worker 직접 계산 문구와 바이트 단위로 같다. 5종 모두 테스트한다.
     - 허용 밖 쓰기가 어댑터에서 거부된다.
     - 전체 테스트 통과
3. **테이블과 Worker 읽기 경로** (migration과 배포 승인 필요)
   - 완료 기준
     - 테스트: 조건 4가지 각각이 어긋나면 직접 계산하고, 맞으면 저장 문구와 기준 시각이 나온다.
     - 운영 migration 전에 Time Travel bookmark(복구 지점)를 기록하고, migration 뒤 기존 행 수가 그대로다.
     - 배포 뒤 webhook 403이 나온다.
4. **precompute workflow**
   - 완료 기준
     - 수동 실행이 성공하고 5종의 행이 저장된다.
     - 로그에 문구, 종목, 금액이 없다.
     - 운영 `/모으기`에 기준 시각이 붙고, CPU가 10ms 미만이다(`logs`로 확인).
5. **계획 변경 시 재계산 요청** (사용자가 토큰을 만들고 Worker secret에 넣어야 함)
   - 완료 기준
     - 테스트: 변경 명령 성공 시 요청 1건이 나가고, 실패해도 명령 결과는 같다.
     - 운영: `/모으기설정` 뒤 몇 분 안에 `/모으기`가 새 계획으로 나온다.
6. **보고서와 신호 갱신 이전**
   - 완료 기준
     - 다음 평일 08:00 일간보가 제시간에 한 번만 도착한다.
     - 정기 실행 CPU가 10ms 미만이다.
     - 신호가 매시간 갱신된다(캐시 시각으로 확인).
7. **문서화**: 단계별 측정값, 결정, 남은 이슈를 이 문서와 상위 문서에 기록한다.

## 되돌리기

- Worker: Actions `rollback`으로 직전 버전에 돌아간다. 저장 결과를 읽지 않으면 기존과 똑같이 동작한다.
- Actions: workflow를 끄면 저장 결과가 2시간 뒤 쓸 수 없게 되고, Worker가 직접 계산으로 돌아간다.
- 테이블: 남겨 두어도 영향이 없다. 지우려면 별도 승인을 받는다.

## 확인이 필요한 것

- 저장 결과 사용 기한 2시간이 괜찮은지
- 단계 5의 GitHub 토큰을 Worker에 넣는 것에 동의하는지

## 단계별 기록

### 1단계 코드 (2026-11-27)

- 사용자가 설계를 확인했다("진행해", 2026-11-27). 사용 기한 2시간과 단계 5의 토큰도 이대로 진행한다.
- 추가: `deploy/cloudflare-js/collate.mjs` `collate(a, b)`
  - 문자열 정렬 규칙(root collation)을 직접 계산한다. 다음 문자에서 `localeCompare`와 같은 결과를 낸다.
    - 출력 가능한 ASCII: 기호 < 숫자 < 영문. 대소문자는 마지막에 비교하고 소문자가 앞이다.
    - 한글 완성형 음절: 영문 뒤, 글자 코드 순
  - 그 밖의 문자가 하나라도 있으면 `localeCompare`로 넘긴다. 그래서 순서는 절대 바뀌지 않는다.
- 교체: `localeCompare` 16곳
  - `aggregation`, `allocation-policy`, `cloud-gateway`, `command-router`, `plan-history`, `rebalance`
- 테스트 `tests/cloud_js_collate.test.mjs` 3개
  - 무작위 문자열 10만 쌍이 `localeCompare`와 같다. 작업 중 별도로 30만 쌍도 확인했다.
  - 실제 키 모양(종목 키, 증권사 이름, 한글 묶음 이름)과 모델 밖 문자(악센트, 이모지, 탭, 자모)의 정렬 결과가 같다.
  - Worker 모듈에 `localeCompare` 직접 호출이 남지 않았다.
- 결과
  - JS 180개 통과
  - Python 233개 통과·1개 건너뜀
  - ruff 통과, 이관 점검 통과
